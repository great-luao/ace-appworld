## DOCS LOOKUP
[sk-00001] When inspecting API docs, ground follow-up calls in the full returned endpoint schema: use the exact API name, required parameter names, auth/token requirements, and response shape shown in the doc object instead of inferring a simplified signature from the task wording or from similar endpoints.
[sk-00003] When looking up an auth/login API, capture the full documented interface before proceeding: endpoint path, required parameters, and the complete success schema, including any token metadata such as token_type, rather than assuming a minimal access_token-only response.
[sk-00008] When checking docs for a collection/listing API, capture the complete success schema—including metadata and any nested ids or related-object references—instead of assuming only the obvious display fields are relevant.
[sk-00010] When you inspect an app's API descriptions, record the full list of available endpoints and scan for companion actions needed to complete the workflow, rather than focusing only on the single endpoint you expected to find.
[sk-00014] When checking docs for a create/update action, record the full success response schema—including confirmation or status fields as well as any returned ids—before planning how you will verify the mutation succeeded.
[sk-00016] When inspecting docs for a search/list endpoint, explicitly record whether authentication is required and carry forward any required access token parameter before planning the next call; do not assume read-only collection endpoints are public.
[sk-00020] When inspecting docs for a search/list endpoint, record the full set of retrieval controls—not just the query field—including auth requirements, filters, pagination limits, and sort options, so later fetches can be made complete and intentionally ordered.
[sk-00025] When checking docs for a create/update filesystem action, record optional behavior-control parameters as well as required inputs—especially flags like recursive creation that determine whether the mutation will work when parent paths may be missing.
[sk-00015] When checking login docs, verify what real-world identifier the credential field expects (for example email vs phone number) from the parameter description instead of assuming it matches another app with a similar auth schema.
[sk-00002] When inspecting APIs, do not assume a callable exists from its likely name. First confirm the exact API names from the app's API list, and prefer separate or incremental doc lookups so one invalid name does not prevent collecting other docs.

## AUTH
[sk-00004] After fetching stored credentials, inspect the full returned list and select the exact password for the target app from the actual records before attempting login.
[sk-00018] After an auth call succeeds, capture and reuse the exact returned access artifact fields and values as-is for subsequent requests; do not invent placeholder tokens or normalize details like token_type casing.

## READ FETCH
[sk-00029] When reading a file or record, do not assume preview-style fields like path/content/size; inspect the actual returned object and use its concrete field names and full content before extracting values for the next step.
[sk-00013] When a task depends on identifying a subset within a transaction/feed list, collect the complete result set across pages for the broad server-side filters you can apply, then explicitly filter the returned records by the decisive criteria (such as participant identity, date window, or direction) before taking action.
[sk-00022] Before narrowing a read with optional filters such as tags or categories, verify from observed records or docs that the target items actually use that field/value; if not, fetch more broadly first and then filter locally.
[sk-00030] When using a search endpoint to identify a person or account, do not assume the query returns a unique match even if you search by a highly specific field like email. Inspect the returned candidate set and confirm the exact record by matching decisive fields from the response before taking action.
[sk-00005] When collecting records from paginated library/listing APIs, keep fetching until a page is empty or the API’s stopping condition is reached, and base downstream decisions on the actual accumulated results rather than expected counts.
[sk-00009] When fetching objects by id, treat every field value as environment-provided state and wait for the returned records before using titles, artists, links, genres, or popularity metrics in downstream steps.
[sk-00011] When an API returns the allowed category or relationship labels used by the environment, use the exact returned values for downstream filtering or matching instead of assuming a standard set of labels.
[sk-00012] For time-sensitive tasks, fetch the environment’s current date/time first and use the returned value and format directly when computing recency windows or date filters instead of assuming the current timestamp.
[sk-00017] When searching for people or contacts, do not assume the query returns one exact match. Inspect all returned candidates and confirm identity with fields like full name, email, phone number, relationship, or shared work details before using a record in a downstream action.
[sk-00019] When fetching time-filtered records, derive the date window from concrete environment evidence (such as note timestamps, task wording, or the environment’s current date) before querying, and treat an empty result as a signal to re-check the chosen date range rather than assuming the expected records exist there.
[sk-00024] When listing filesystem contents, use the returned paths as the source of truth for what exists—capture the actual filenames, count, path format, and extensions from the listing before planning moves or filters instead of assuming a small set of standard image names.
[sk-00026] When a text search returns multiple candidate records, do not assume the intended item is the only or top match. Review the returned titles/tags first, then fetch full details for the most relevant candidate records before choosing one for a downstream action.
[sk-00027] When reading paginated search results, verify each returned page’s actual records before using them; do not assume later pages will continue the same pattern, relevance, or query-specific theme seen on the first page.
[sk-00028] When searching the filesystem for a task document, do not assume a single obvious filename or location. Inspect the returned candidate paths and use concrete cues in the filenames or directory structure (such as dates or document type) to identify the likely target, then open the candidate file(s) to confirm before taking downstream actions.

## LOCAL REASONING
[sk-00021] When working with values already fetched from a tool, do not rely on memory for their structure; inspect the actual object or the earlier observation and use its real field names and formats before reasoning from it.
[sk-00006] Before trusting a derived count from multiple fetched collections, inspect a few sample records from each source and verify that the identifiers you are unioning are the same entity key and have the overlap you expect.
[sk-00023] When you derive person matches from search results across apps, do not assume each query yields a single clean match. Inspect the actual candidate lists and reconcile entities using concrete shared fields such as first/last name, email, friendship status, or relationship tags before deciding who is paid or whom to request.
[sk-00007] When doing local data formatting in the sandbox, do not assume standard helper modules or constructors are permitted. If a module/function is blocked, switch to simple built-in string/list operations to build the required output and verify with a small preview before proceeding.
