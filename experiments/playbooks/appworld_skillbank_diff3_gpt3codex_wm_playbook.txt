## DOCS LOOKUP
[sk-00001] During API doc lookup, verify and retain the complete success response schema (including extra fields and precise types/formats), not just the minimal fields needed to identify the endpoint.
[sk-00002] When calling an API doc, design the call carefully to extract the most needed and useful information, avoiding over extraction of details that may not be relevant for the task at hand. Focus on key parameters, response fields, and usage examples that directly inform the agent's decision-making.
[sk-00021] After listing API descriptions, parse the returned objects directly and copy exact API names/fields from the docs before planning calls; do not rely on guessed names or alternate naming conventions.
[sk-00023] Treat API docs as the source of truth and copy exact request/response schema details (path, pagination defaults/limits, and nested field keys/types) into the next call plan; do not rely on inferred REST patterns or remembered field names.
[sk-00027] When reading API docs, explicitly capture which parameters are optional vs required, their defaults, and any control flags (e.g., overwrite) before composing the call; also carry forward the full success schema so you can validate outcomes using all returned fields.
[sk-00029] When reviewing endpoint docs, explicitly check whether detail/read endpoints require authentication even if related list endpoints already used a token; copy the full required-parameter list (including access_token) before planning calls.
[sk-00034] After fetching an endpoint doc, immediately build the next-step call plan from the returned schema verbatim: required auth params, exact filter names, path, and response field keys. Do not predict or reuse generic endpoint patterns across apps before copying these exact fields.
[sk-00003] If you find yourself missing decisive information after an API doc lookup, consider revisiting current doc or its upper one with a more targeted query or using additional resources to fill in the gaps. But also avoid over extracting information that may not be relevant to the task at hand.
[sk-00025] During API doc lookup, extract both success and failure response schemas and any metadata fields (e.g., token_type, casing, method/path) before proceeding; don’t assume only the primary payload field is needed.
[sk-00026] When calling an API-doc endpoint, treat the result as interface schema, not business data: explicitly capture required parameters, optional pagination controls/defaults, and key response field names before making the next API call.
[sk-00030] When reading endpoint docs, explicitly verify whether the endpoint requires auth (e.g., access_token) even if similar read endpoints did not; record all required parameters from the parameters list before assuming callability.
[sk-00038] After a 'no such API' error, re-run the app’s API list and choose the next endpoint name strictly from the returned names; do not invent likely names. Then open that exact endpoint doc before assuming parameters or path.
[sk-00044] When reading API docs for detail endpoints, capture the exact nested shape of the success payload (e.g., whether related items are returned as IDs or embedded objects, and their field names) before planning follow-up calls.
[sk-00046] When reading list-endpoint docs, explicitly capture optional ordering/filter parameters and any metadata fields added to each item (e.g., liked_at timestamps), including defaults, before writing the fetch loop.
[sk-00004] Even when two apps expose similarly named endpoints (like login), verify app-specific parameter semantics in the docs (e.g., email vs phone_number) before constructing request inputs.
[sk-00032] When reading API docs, copy request parameter names and response fields exactly as documented; do not infer friendlier aliases or fixed success text from endpoint descriptions.
[sk-00005] Do not assume a callable exists from its likely name. After a wrong action, it's better to first confirm the exact API names from the app's API list, and prefer separate or incremental doc lookups so one invalid name does not prevent collecting other docs.
[sk-00028] When using api_docs endpoints, expect metadata (method, params, schema) rather than live record counts or object data; use the doc output to plan the next callable data-fetch step.

## AUTH
[sk-00006] When obtaining credentials or a login response, inspect the full returned structure and retain any account identifiers, token metadata, or session fields that may matter for the next authenticated call, not just a guessed password or a bare token string.
[sk-00007] Before attempting login, verify the exact auth input schema from docs and map stored account data to those concrete parameter names and identifier types instead of guessing generic fields like username, email, or password.
[sk-00008] If the available credential or profile information does not yet identify the exact account to use, fetch the missing identity detail first and only then attempt login, rather than retrying auth with partially matched credentials.
[sk-00022] After calling a credential-retrieval API, read and preserve the complete returned account/password entries (including the exact target service) before attempting login; do not proceed with placeholder or partial credential assumptions.
[sk-00009] After an auth-related call, reuse the exact returned access artifact fields and values as environment truth for later requests, rather than normalizing, renaming, or inventing token or session details.
[sk-00033] When fetching stored account credentials, treat the returned list as source of truth: locate the exact entry for the target app/account and use that exact password or secret in the next auth call instead of guessed or placeholder values.
[sk-00010] When a login or access step fails, do not keep retrying variants blindly. Use the failure to check prerequisites such as the correct credential source, identifier type, and any required auth or setup step before the next action.

## READ FETCH
[sk-00011] A successful read step may still be too shallow for the next decision. Inspect representative returned records, pagination metadata, and any omitted fields before treating the fetch as complete.
[sk-00012] Use the actual response structure from the fetch result - real keys, nesting, and id formats - in downstream code instead of assuming common field names like items, results, id, or content.
[sk-00013] When the next step depends on selecting or comparing records, gather a broad enough result set first, including additional pages when needed, and then filter locally by the decisive criteria.
[sk-00014] Base downstream decisions on the values actually returned by the environment, including ids, statuses, timestamps, and counts, rather than on expected record state or guessed matches.
[sk-00031] When merging records fetched from multiple collections, do not predict the final unique count from intuition; compute and inspect per-source counts and ID overlaps from the returned data before relying on an expected total.
[sk-00036] When a text search returns many plausible matches, do not assume the intended record from title/query alone; use returned note IDs to fetch full details (or apply stricter filters) before selecting a record for downstream actions.
[sk-00037] When searching users by a common name, expect many unrelated results; do not treat raw search output as a confirmed match. Cross-check candidates with additional observed signals (e.g., friendship status, prior transaction counterparties, exact name/email alignment) before selecting recipients for downstream actions.
[sk-00041] When fetching a known record (e.g., by ID), do not assume or reconstruct its text content from the task prompt or title. Read the returned body verbatim and extract entities/amounts only from the observed content before taking follow-up actions.
[sk-00042] When using transaction history to infer who has already paid, do not rely on raw direction-only results or expected names/amounts; filter the fetched transactions by task-relevant evidence (e.g., recent date window, matching event description, and counterparties) before deciding whom to request.
[sk-00043] For list endpoints (especially paginated ones), do not assume the collection is empty before fetching; iterate pages until exhaustion and compute count/aggregate metrics from the returned items before deciding the data is insufficient.
[sk-00045] When computing totals from fetched detail records, verify that the specific value fields you’re summing are actually present in the returned objects (and not silently defaulting via .get(..., 0)); if aggregates look unexpectedly zero, inspect one raw item or the API schema before trusting the result.
[sk-00047] When file search returns multiple date-stamped matches, do not assume a single intended document from the query text; inspect the returned paths and select the task-relevant period (e.g., latest month) before reading or acting on a file.
[sk-00048] When a recursive directory listing returns a large tree, don’t continue assuming an expected folder structure. Use the observed paths to refine the next fetch (e.g., restrict directory_path or apply substring/entry_type filters) and then read only candidate files relevant to the task.
[sk-00015] If a read returns empty, partial, or surprising results, broaden or verify the query first - such as filters, page index, or identifier assumptions - before switching to a write action or concluding the target data does not exist.

## LOCAL REASONING
[sk-00016] Before acting on a locally derived summary, keep the decisive supporting details visible - such as which records matched, tie cases, or boundary values - when those details could change the next step.
[sk-00017] When reasoning over previously fetched data, re-check the actual field names and value formats from the observation before writing code that joins, filters, or aggregates them.
[sk-00018] If a local decision depends on several conditions, inspect intermediate subsets or counts before finalizing the conclusion so the next action is grounded in enough evidence.
[sk-00039] Before taking action from free-form records, transform the relevant fields into a structured intermediate result (e.g., person and amount) and explicitly mark unresolved parts (such as duplicates or already-settled entries) so downstream actions are based on complete decision-critical data.
[sk-00019] When deriving counts, matches, or rankings from fetched data, verify that your normalization and comparison logic matches the real value formats and entity keys before using the result downstream.
[sk-00035] For date-window calculations, derive and use the environment’s actual current date at runtime instead of assuming today’s real-world date; print or verify computed bounds before applying them to API filters.
[sk-00040] Before marking someone as already handled based on prior transactions, avoid loose substring name matching over broad history; first narrow to relevant transactions (e.g., by date/description/amount) and use stronger identity linkage (exact email/contact mapping) before excluding them from pending actions.
[sk-00020] If local reasoning produces an empty set, impossible count, or surprising winner, debug the assumption with a small intermediate print or sample check before taking the next environment action.
[sk-00024] When local transformation code fails due to a disallowed module/function, treat it as an environment capability constraint and immediately rewrite using permitted primitives (basic string/list operations) instead of trying nearby blocked helpers.
