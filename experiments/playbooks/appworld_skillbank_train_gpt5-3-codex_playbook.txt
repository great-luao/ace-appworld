## DOCS LOOKUP
[sk-00005] During API doc lookup, verify and retain the complete success response schema (including extra fields and precise types/formats), not just the minimal fields needed to identify the endpoint.
[sk-00002] When consulting API docs, treat the returned path and response schema as the source of truth: copy exact endpoint/method and only rely on fields explicitly documented, rather than inferring extra keys or route patterns.
[sk-00009] When you call an API-description/listing endpoint, treat the returned list as authoritative: use exact API names from the response and avoid inventing, renaming, or omitting operations before selecting the next doc call.
[sk-00014] When reading an API doc, extract the complete callable contract before proceeding: include all optional filter/pagination parameters (with defaults/constraints) and mirror response field names/types exactly (including pluralized or nested fields), rather than collapsing them into guessed generic keys.
[sk-00001] When reading API docs, capture the full contract (required params, method/path, success fields, and failure schema) before planning the next action; do not assume omitted fields are irrelevant.
[sk-00028] Even for similarly named library endpoints, verify resource-specific optional filters and item schema fields (including nested objects and ID lists) from the doc itself before planning follow-up queries.
[sk-00034] When you query API descriptions, treat the returned list as a capability inventory: read/record all available endpoints before selecting one, rather than assuming a small subset of familiar actions.
[sk-00011] Even when two apps expose similarly named endpoints (like login), verify app-specific parameter semantics in the docs (e.g., email vs phone_number) before constructing request inputs.
[sk-00017] For action endpoints, verify the exact documented success payload before planning downstream reads or parsing fields; do not assume state fields (e.g., counts/ids) will be returned unless the schema explicitly includes them.
[sk-00036] When consulting API docs, copy exact documented interface values (e.g., path strings and key identifiers) rather than inferring format from similar APIs or naming patterns.
[sk-00018] Before calling show_api_doc for a specific endpoint, first list the app’s available APIs (e.g., show_api_descriptions) and use an exact name from that list; if a doc lookup fails, re-enumerate names instead of guessing variants.
[sk-00022] When using documentation endpoints (e.g., show_api_doc), expect interface metadata (parameters, method, response schema), not business data results; use docs output to plan the next API call rather than to estimate fetched values.

## AUTH

[sk-00012] When retrieving credentials from a password store, treat the response as the source of truth: enumerate/search the full returned accounts and select the credential by exact account_name before attempting login.
[sk-00006] In credential-retrieval steps, ground follow-up actions in the exact returned account/password pair (selected by account_name) rather than assumed placeholders or partial lists.

## READ FETCH
[sk-00031] Before using search results to choose target users, inspect the API’s response schema and parse the returned fields exactly as provided (e.g., separate name parts, email, relationship indicators) instead of assuming a simplified object shape.
[sk-00044] When fetching a record/object (e.g., file details), treat the returned payload schema as authoritative and map downstream logic to the actual keys present, not guessed field names from similar APIs.
[sk-00027] When answering a comparison question over a library (newest/oldest/highest), fetch all relevant candidate records and compute the result from returned fields before finalizing; do not rely on placeholder output or partial evidence.
[sk-00029] Before creating outbound requests or messages, fetch existing pending/outstanding records and compare key fields (recipient, amount, note/description) so you only create missing items and avoid duplicates.
[sk-00043] When using search to decide whether to create a new item, fetch enough pages and then explicitly filter for exact match fields (such as exact title and correct owner) before concluding it already exists or needs creation.
[sk-00004] When collecting paginated records, treat the fetched pages as the source of truth for totals and state; continue until the API’s stop condition is met, then base counts/decisions on the accumulated results rather than expected volume.
[sk-00007] When selecting an item by a metric (min/max play_count, latest timestamp, highest score), derive the result strictly from the returned values across the full candidate set and do not assume which item will win before comparison.
[sk-00010] When fetching records in a loop for specific target IDs (especially with optional filters like user_email), verify each returned record’s key IDs and keep only records that match the current target/candidate set before building decision maps.
[sk-00013] When an API returns a list of categorical labels (e.g., relationship types, statuses, tags), do not assume the exact vocabulary in advance; first read the returned set and then map task terms to those observed labels before filtering or deciding.
[sk-00015] When collecting records across multiple filter values that may overlap, treat the combined result as a union and deduplicate by a stable key (for example, record ID) before counting, matching, or using the set for next-step queries.
[sk-00016] For volatile state reads (for example current time/date, live balance, or status), treat the API response as the sole source of truth and avoid assuming concrete values in advance; parse and use the returned format before applying time-based filters or comparisons.
[sk-00021] When aggregating items fetched through multiple parent collections (e.g., direct library plus albums/playlists that reference the same items), assume heavy overlap and compute final counts only after building a deduplicated union keyed by stable IDs from responses.
[sk-00023] When a fetched record contains free-form text (notes, descriptions, message bodies), do not assume the exact contents; read and parse the returned text to extract the required output fields before replying or transforming.
[sk-00024] When searching people/contacts by a broad query (e.g., first name), treat results as a candidate list and explicitly disambiguate the target using additional observed fields (phone number, relationship, full name, recent message context) before sending or updating anything.
[sk-00033] When iterating through fetched item details to filter by a categorical field (e.g., genre/status/type), do not assume the filtered set will be empty or non-empty in advance; compute membership strictly from observed field values in each response and base downstream actions on that derived set.
[sk-00035] When listing files from a directory for later aggregation, treat the returned paths as the source of truth and derive selection rules from observed structure (actual subdirectories, filename date formats, and extensions) before reading or summing; do not assume expected file names or a flat layout.
[sk-00037] When a file-organization rule depends on time state (e.g., month created/modified), treat the directory list as inventory only; fetch per-file metadata and classify from observed timestamps before moving files, instead of inferring from filenames or expected counts.
[sk-00039] When computing totals from nested fetches (e.g., parent records -> child details), validate that each child response actually contains the metric field you plan to aggregate; if the field is missing, treat the result as incomplete and inspect the child schema/alternate endpoint before making duration/count-based decisions.
[sk-00041] Before batch file operations that depend on folder layout, list the immediate subdirectories at the exact target path and treat that inventory as authoritative; if expected source folders are missing or only output/staging folders appear, adjust scope (or re-check parent paths) before proceeding.
[sk-00042] When listing directories for batch processing, validate path depth explicitly: list the target path, and if results show only a container/staging folder instead of expected work folders, re-list inside that returned folder (or move up one level) before selecting items to process.
[sk-00045] When using a text query to find a record for update, treat search results as candidates (not a guaranteed unique match): inspect returned identifiers and titles, then select the exact target record explicitly before fetching details or modifying.
[sk-00046] When using search endpoints to locate a specific entity, treat results as a candidate list even if a full name is provided; explicitly filter returned records by exact identifying fields (e.g., exact name) before selecting an ID for downstream fetches or comparisons.

## LOCAL REASONING
[sk-00030] After printing or inspecting fetched records, immediately derive the decision-ready representation (e.g., parsed entities, amounts, and filters for exclusions) before taking the next API action; do not leave critical fields embedded in raw text.
[sk-00008] When deriving a specific value from local parsing/filtering rules, don’t predict the final item by intuition—inspect the exact input ordering and rule trigger (e.g., first match vs all matches), and print/check the intermediate candidates before committing to a concrete output.
[sk-00025] For time-based filters computed locally (e.g., last N days), avoid hard-coding or assuming today’s date in predictions; first read/print the runtime date and derive bounds from it before expecting concrete date values.
[sk-00026] When combining multiple local collections (e.g., unions of IDs from songs/albums/playlists), compute and inspect per-source counts and overlap/unique totals before predicting concrete final counts or value ranges.
[sk-00032] For local money totals built from filtered transactions, verify the intermediate set and amount semantics before predicting the final sum: print a small sample of matched rows, confirm the identity key used for matching (e.g., sender/recipient email), and confirm whether `amount` is signed or absolute for that direction.
[sk-00038] When selecting an item from already-fetched local records (e.g., max/min/filter), treat non-selection fields as fixed to the source object: verify by printing the chosen record directly and avoid predicting inferred metadata values (ratings, timestamps, visibility, IDs) that were not recomputed.
[sk-00040] When computing totals from per-item attributes (e.g., playlist duration from song durations), avoid predicting concrete final numbers until you inspect the computed components: print per-item values for at least one candidate and verify the exact field and unit being summed before expecting exact totals.
[sk-00019] When local formatting code fails with a sandbox restriction (e.g., module/function not allowed), treat that as an environment constraint and immediately rework the transformation using simpler allowed string/list operations instead of retrying equivalent blocked helpers.
[sk-00020] Before assuming local transformation code will fail due to data-shape issues, run a minimal sanity check on the in-memory object structure (e.g., sample type/key access) and then proceed with the simplest direct implementation.
