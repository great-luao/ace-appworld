## DOCS LOOKUP
[sk-00001] During API doc lookup, verify and retain the complete success response schema (including extra fields and precise types/formats), not just the minimal fields needed to identify the endpoint.
[sk-00002] During docs lookup, use the documentation response schema verbatim: confirm exact field names and structure in both endpoint listings and per-endpoint docs (including parameter names and success/failure response keys) before planning calls.
[sk-00003] During API doc lookup, extract the full callable contract before proceeding: endpoint/method, required params, success fields, and failure schema. Do not assume omitted response fields are absent; verify them explicitly from the docs before planning the next step.
[sk-00033] After listing available APIs, choose the next `api_name` exactly from that returned list and fetch its doc before planning arguments; do not substitute guessed synonyms (e.g., request/pay/charge variants) or inferred field names.
[sk-00038] When calling an API index/description listing, treat the returned list as decision-critical: read and account for all listed endpoints before choosing the next doc to inspect, rather than proceeding from a guessed subset.
[sk-00043] When inspecting list/retrieval API docs, explicitly enumerate optional filtering/search/sorting parameters (and their defaults/interaction rules), not just required auth and pagination fields, before planning fetch calls.
[sk-00004] Even when two apps expose similarly named endpoints (like login), verify app-specific parameter semantics in the docs (e.g., email vs phone_number) before constructing request inputs.
[sk-00025] When API docs show a response field as a generic type (e.g., "message": "string"), do not predict or hard-code exact literal text; treat only the presence/type as guaranteed unless an enum or fixed value is explicitly documented.
[sk-00040] During docs lookup, do not predict or rely on guessed endpoint paths/descriptions; read and use the exact returned interface values (e.g., route strings) as authoritative for subsequent calls.
[sk-00044] When docs specify valid values for a parameter (e.g., sort_by attributes), treat that set as exact for that endpoint and do not copy extra values from similar endpoints.
[sk-00048] For update/mutation endpoints, verify the success response schema in docs before planning next steps; do not assume the API returns the updated resource unless explicitly documented.
[sk-00005] Do not assume a callable exists from its likely name. After a wrong action, it's better to first confirm the exact API names from the app's API list, and prefer separate or incremental doc lookups so one invalid name does not prevent collecting other docs.
[sk-00028] Match your expected output to the function type you are calling: doc-inspection APIs return interface metadata (parameters/schema), not business data results. Use docs calls to learn how to make the subsequent data call, then predict data from that runtime call instead.

## AUTH
[sk-00006] When obtaining credentials or a login response, inspect the full returned structure and retain any account identifiers, token metadata, or session fields that may matter for the next authenticated call, not just a guessed password or a bare token string.
[sk-00007] Before attempting login, verify the exact auth input schema from docs and map stored account data to those concrete parameter names and identifier types instead of guessing generic fields like username, email, or password.
[sk-00008] If the available credential or profile information does not yet identify the exact account to use, fetch the missing identity detail first and only then attempt login, rather than retrying auth with partially matched credentials.
[sk-00023] After retrieving saved credentials, parse the returned account list and extract the exact username/password pair needed for the target app before attempting login; do not proceed based on assumed or placeholder credentials.
[sk-00009] After an auth-related call, reuse the exact returned access artifact fields and values as environment truth for later requests, rather than normalizing, renaming, or inventing token or session details.
[sk-00021] When retrieving stored credentials, treat the returned account/password pairs as the source of truth: locate the exact target account entry and pass that exact password to login, rather than assuming placeholder or remembered values.
[sk-00010] When a login or access step fails, do not keep retrying variants blindly. Use the failure to check prerequisites such as the correct credential source, identifier type, and any required auth or setup step before the next action.

## READ FETCH
[sk-00011] A successful read step may still be too shallow for the next decision. Inspect representative returned records, pagination metadata, and any omitted fields before treating the fetch as complete.
[sk-00012] Use the actual response structure from the fetch result - real keys, nesting, and id formats - in downstream code instead of assuming common field names like items, results, id, or content.
[sk-00013] When the next step depends on selecting or comparing records, gather a broad enough result set first, including additional pages when needed, and then filter locally by the decisive criteria.
[sk-00046] When searching for an existing object by name returns many matches, collect decisive disambiguators (e.g., your own account identity and exact-name match) and filter on them before deciding create-vs-reuse.
[sk-00014] Base downstream decisions on the values actually returned by the environment, including ids, statuses, timestamps, and counts, rather than on expected record state or guessed matches.
[sk-00022] When building an id-to-record map from filtered list endpoints, verify each returned record’s key (for example, song_id) matches the current query target set and ignore or separately handle out-of-scope records before using the map for decisions.
[sk-00024] When aggregating records from multiple filtered fetches, expect overlap between filters and deduplicate by a stable identifier (for example, contact_id) before using the result set downstream.
[sk-00026] When merging entities from multiple read endpoints, track unique-id count after each source (and optionally new ids added) instead of assuming expected overlap; use these observed increments for downstream expectations.
[sk-00032] When using name-based search endpoints, assume results may be broad or loosely matched; collect candidates, then explicitly filter/score by decision-relevant fields (for example exact name components, friendship status, or known transaction links) before selecting targets for next actions.
[sk-00034] Treat text search results as candidate sets, not final targets: after collecting matches (and paginating as needed), shortlist by metadata and then fetch full records by id to confirm relevance before making downstream updates or requests.
[sk-00036] For fetched records that contain free-text fields (notes, descriptions, messages), treat the text as unknown until read verbatim from the response; do not infer specific names, amounts, or paid/unpaid status from the title or prior expectations before extracting structured data.
[sk-00037] When a history endpoint returns many valid records, treat them as candidates and explicitly filter to task-relevant matches (for example by counterparty identity, amount, time window, and description) before inferring status like "already paid."
[sk-00039] After recursive directory reads, treat returned paths as a mixed candidate pool and explicitly filter by task-relevant path segments (e.g., service folder, date window, file type) before opening files or aggregating values.
[sk-00041] In filesystem organization tasks, treat directory listings as candidate paths only; do not assume expected filenames or counts from the prompt. First use the returned paths, then fetch per-file metadata (e.g., created/updated timestamps) needed to classify files before moving them.
[sk-00042] When aggregating values from fetched records across endpoints, verify the exact response field names/units used for the metric (for example duration fields) before summing; if totals look implausible (e.g., non-empty list but zero total), inspect a sample raw record and adjust extraction.
[sk-00045] In filesystem read steps, treat each directory listing as the source of truth for current structure and names: use the returned paths directly for subsequent compression/deletion loops, and do not infer expected subdirectories from the task text.
[sk-00015] If a read returns empty, partial, or surprising results, broaden or verify the query first - such as filters, page index, or identifier assumptions - before switching to a write action or concluding the target data does not exist.

## LOCAL REASONING
[sk-00016] Before acting on a locally derived summary, keep the decisive supporting details visible - such as which records matched, tie cases, or boundary values - when those details could change the next step.
[sk-00017] When reasoning over previously fetched data, re-check the actual field names and value formats from the observation before writing code that joins, filters, or aggregates them.
[sk-00018] If a local decision depends on several conditions, inspect intermediate subsets or counts before finalizing the conclusion so the next action is grounded in enough evidence.
[sk-00019] When deriving counts, matches, or rankings from fetched data, verify that your normalization and comparison logic matches the real value formats and entity keys before using the result downstream.
[sk-00029] When multiple extracted candidates can satisfy a condition, don’t rely on incidental parse order; apply an explicit selection rule (e.g., recency, user request constraint, or all matches) and verify the chosen value against the source text before using it.
[sk-00030] For local date/time calculations used as API filters, derive bounds from the environment’s current runtime date/time and treat those computed values as the source of truth instead of predicting calendar values from memory.
[sk-00031] When combining entities from multiple local collections, validate the merged scope with quick diagnostics (per-source counts, overlap sizes, and min/max key ranges) before predicting concrete totals or downstream winners.
[sk-00035] When reconciling people across local datasets (e.g., note names vs transaction senders), don’t mark status changes from loose substring matches alone; require a stronger identity match (exact normalized full name/email or validated contact mapping), and keep ambiguous matches unresolved until verified.
[sk-00047] After local filtering/sorting to identify a target record, treat the computed top candidate’s fields (e.g., id, amount, counterpart identifiers) as the source of truth and read them directly for the next action instead of relying on guessed historical values.
[sk-00020] If local reasoning produces an empty set, impossible count, or surprising winner, debug the assumption with a small intermediate print or sample check before taking the next environment action.
[sk-00027] When doing local data transformation, do not assume all Python modules/functions are permitted; if an import or function is blocked, switch to a simpler allowed string/list-based construction instead of retrying restricted utilities.
